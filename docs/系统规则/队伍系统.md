## 1. 数据模型与不变量

| 项 | 规定 |
| --- | --- |
| `members: Array[String]` | 编队角色 id 数组，**上限 3**，有序（插入序即编队序，供战斗上阵顺序参考） |
| `companion_id: String` | 同行角色 id，**空串 = 无同行**；必须 ∈ members（同行不额外占第 4 席） |
| 地图表现 | 同行**只占编队数据，不生成任何地图实体/跟随者**（架构 §1.3：地图仅主角移动） |
| 体系来源 | 角色体系唯一来源 = `characters.csv` 的 `system` 列（机律/秘法/玄门）；与星髓体系无关（星髓是装备槽，归 T6.5） |
| Autoload 顺序 | Party 依赖 DataManager（查体系）与 EventBus（发信号），注册位置**必须在其后**（建议 …→EventBus→Party→GameState） |

## 2. API 行为规则

**返回值统一契约**：以下 API 均返回 `bool`，语义 = **「本次调用是否成功产生了数据变更」**。变更成功 true；拒绝或无变化 false（幂等操作返回 false 不算错误，不崩溃）。拒绝/无变化原因写 `push_warning` 日志（含原因短语）。**信号只在返回 true 时发出**（见 §3）。

| API | 触发条件 → 行为 | 边界 |
| --- | --- | --- |
| `add_member(id)` | id 合法且不在队、未满员 → 追加至 members 末尾，true | ① id 在 characters.csv 查不到 → 拒绝 false；② 已在队 → false（幂等）；③ **满员（3/3）→ 拒绝 false，不自动替换**（见 §2.1） |
| `remove_member(id)` | id 在队 → 移除，true | ① id 不在队 → false（幂等）；② **移除的恰是 companion_id 所指角色 → 同步清空 companion_id，仍只发一次信号**（一次调用一次变更一次信号） |
| `set_companion(id)` | id ∈ members → 置 companion_id = id，true | ① id 不在 members → **拒绝 false，不隐式 add_member**；② id 已是 companion → false（无变更） |
| `clear_companion()` | 有同行 → 清空 companion_id，true | 无同行 → false（幂等无变更） |
| `is_full()` | 查询，恒不发信号 | members.size() == 3 |
| `has_member(id)` | 查询，恒不发信号 | — |
| `get_members()` | 查询，返回 members 副本 | 调用方改副本不影响 Party 内部数据 |

### 2.1 满员时 add_member：拒绝，不替换（拍板）

- **决策**：编队是玩家在 UI 的显式操作，**替换权在 UI 层**（「先 remove 再 add」两步完成，各自发信号）；Party 数据层不做隐式替换，保证数据可预期、信号不重复。
- UI 层满员时提示「编队已满，请先移除一名角色」（文案归剧情文案润色）。
- T5.2 同行任务满员场景因此**不崩溃**：CompanionManager 调 `set_companion(id)`，任务角色不在编队时收 false，按引导让玩家编入即可（推进表 T5.2 明确引用本规则）。

## 3. 信号契约 party_changed

- EventBus **需先注册**：`signal party_changed(party_list: Array)`（当前 EventBus.gd 尚无此信号，T2.2 实现时先注册后使用）。
- **发送规则**：§2 表中四个变更 API（add_member / remove_member / set_companion / clear_companion）**仅在返回 true 时**发一次 `EventBus.party_changed(party_list)`。
- `party_list` = `get_members()` 快照。**同行者本就 ∈ members，party_list 即 members 原样**：不重复计入、不追加第 4 项。
- 失败/幂等（返回 false）**不发信号**——`party_changed` 严格等价于「编队数据确有变化」。

## 4. team_systems() 体系组合查询

**签名**：`team_systems() -> Dictionary`，返回 `{systems: Array, all_same: bool, has_all_three: bool}`。

| 字段 | 定义 |
| --- | --- |
| `systems` | members 中各角色 system 值数组（按编队序，可含重复，如 `["机律","机律","玄门"]`） |
| `all_same` | **非空且**全员体系相同（单人队 all_same=true，纯数据事实） |
| `has_all_three` | 机律、秘法、玄门**三系各至少 1 人**（上限 3 人 → 恒为「恰好 3 人三系各一」） |

- 基于 `characters.csv` system 列实时查询（不缓存体系副本，CSV 是唯一真相）。
- **边界**：① 空编队 → `{systems: [], all_same: false, has_all_three: false}`，不触发任何机制；② members 中某 id 查不到 CSV 行 → 该角色跳过统计并 push_warning（沿 T0.3 容错风格，不崩溃）。
- 数据层天然互斥：members ≤ 3 时 `has_all_three=true` 则 `all_same` 必为 false，消费方无需处理双真。

## 5. 三态互斥判定（与 T3.5 战斗程序的接口）

T3.5 PartyBonus 消费 `team_systems()`，**判定顺序固定**（先命中先终止）：

```
1. has_all_three == true  → 混元（共振/汇流一律不触发）
2. 否则 all_same == true  → 共振
3. 否则（非空、多于一系、三系未齐，即两系混编） → 汇流
4. 空编队 → 无机制
```

- 互斥是硬约束：混元编组**不得**同时出现共振/汇流的任何效果与日志字样（推进表 T3.5 验收项）。
- 三态的**效果内容**已裁定（制作人01，2026-09-19）并落盘《战斗系统》§4：**共振=三人合击技**（三人大招后自动触发）、**汇流=大招后自动充能 30% + 三人齐后全体拉条 30%**、**混元=全属性增幅 30%**；旧占位数值（共振 atk+10% / 汇流 def+10% / 混元 hp+8%&atk+5%）**作废**。本规则只锁「哪个机制被触发」的判定逻辑，效果实现归 T3.5（按战斗系统 §4）。
- 战斗上阵人数门槛（三人小队）由战斗系统校验，Party 层只提供数据事实。

## 6. 边界情况总表

| # | 情况 | 规定行为 |
| --- | --- | --- |
| 1 | 满员 3/3 时 add_member | 拒绝 false，不替换（§2.1）；UI 引导先移后加 |
| 2 | set_companion 传入不在编队的角色 | 拒绝 false，不隐式入队 |
| 3 | 移除角色即同行者 | 同行关系随移除终止，同步清 companion_id，单次信号 |
| 4 | 空编队调 team_systems / 战斗判定 | 空结果、无机制，不崩溃 |
| 5 | members 含 CSV 查不到的 id | team_systems 跳过该角色并告警；add_member 阶段已拦截，此为防御分支 |
| 6 | 对同一角色重复 add / 重复 set_companion | 幂等 false，不重复发信号 |
| 7 | 存档（架构 §4.2） | Party 序列化 members + companion_id 两项；companion_id 不在 members 属坏档，读档时清空 companion 保留 members |
