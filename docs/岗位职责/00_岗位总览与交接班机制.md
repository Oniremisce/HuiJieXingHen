## 2. 岗位级依赖链

```
制作人·项目统筹 ── 调度/验收 ──→ 全体岗位

策划层（先定义，输出规则与数据）
  系统策划 ──规则──→ 数值策划（把规则落成数值）
  数值策划 ──数值──→ 系统程序 / 战斗程序
  剧情文案策划 ──台词 CSV──→ 剧情对话程序

程序层（后实现，消费策划输入）
  系统程序（P0 底座：Autoload / CSV 管线 / EventBus / GameState）
     ├── 依赖 P0 底座 → 战斗程序
     └── 依赖 P0 底座 → 剧情对话程序

内容层（并行准备，P7 接入）
  美术 ──占位规范/接口──→ 系统程序、战斗程序、剧情对话程序
  音频 ──音频规范────→ 系统程序（T7.3 接入）
```

**关键依赖事实**：

- 战斗程序、剧情对话程序的所有任务卡都依赖系统程序交付的 P0 底座（T0.1\~T0.4）与 P2 数据（T2.1/T2.2）。
- 剧情对话程序依赖剧情文案策划交付台词 CSV（T4.3/T4.4/T5.3）。
- 战斗程序依赖数值策划交付公式与数值（T3.4/T3.5），依赖系统策划确认机制规则。
- 美术在 P0\~P6 只做「占位规范 + 接口配合」，P7（T7.3）才做真实资源接入；接入时以 ArtProvider 接口为准，业务代码零改动。

## 4. 交接班机制（全局规则，所有岗位必须遵守）

### 4.1 交接班表是什么

交接班表是本岗位的**持续工作台账**，作用是让其他 agent（尤其下游岗位）不用反复追问就能知道：

- 你做了哪些事、改动了哪些文件；
- 你定义了哪些**接口约定**（CSV 列、flag 名、信号名、ArtProvider 接口、命名规范）；
- 你留下了哪些**遗留问题 / 待办 / 风险**。

它和 Git commit 互补：commit 是代码级历史，交接班表是人话级说明。

### 4.2 存放位置与文件命名

- 项目内统一目录：`D:\Dev\HuiJieXingHen\docs\handover\`
- 文件命名：`<岗位名>_交接班表.md`，例如 `数值策划_交接班表.md`
- 每岗位一份，**持续追加**，不删除历史行；新内容追加到表格末尾，最新的一行永远在最后。
- 若岗位职责文档部署在项目根目录，则本表与职责文档同目录即可，但**所有岗位必须约定同一个 handover 目录**，便于交叉阅读。

### 4.3 填写时机（何时交班）

只要发生以下任一情况，就必须追加一行：

1. **完成一张任务卡**且验收通过、commit 已提交（最常规的交接点）；
2. 你**改动或新增了对外接口**（CSV 列、flag 名、EventBus 信号、ArtProvider 接口、资源命名）——哪怕任务卡还没整体完成；
3. 你发现**阻塞、风险、依赖缺失**，需要上游或制作人处理；
4. 你**临时离场**（一个波次结束时），给接手者留现场。

### 4.4 交接班表模板（统一列结构）

```markdown
# 《汇界星痕》<岗位名> 交接班表

> 追加规则：每完成一张任务卡 / 每次接口变更 / 每次发现遗留问题时追加一行。
> 下游岗位开工前请先读本表，确认前置就绪与接口约定。

| 日期 | 任务卡 | Agent编号 | 本次做了什么 | 产出/改动文件 | 关键决策与接口约定 | 验证证据 | 遗留问题/待办 | 需通知的下游岗位 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 2026-09-19 | T0.3 | 系统程序01 | 完成 7 张 CSV 初始表与解析器 | data/csv/*.csv、CSVParser.gd、DataManager.gd | 列头按推进表 §2.4；坏行报错含文件+行号 | MCP 日志行数核对通过 | 角色名待剧情文案填 | 战斗程序、剧情对话程序 |
```

**列填写说明**：

- 日期：`YYYY-MM-DD`；任务卡：如 `T4.3`（无任务卡写 `接口变更` / `风险登记`）。
- **Agent编号：必填**。实际执行本行工作的 Agent 编号，格式 `<岗位名><两位序号>`（如 `系统程序01`、`系统策划02`），规则详见 §4.8；同一岗位换 Agent 接力时，各 Agent 用自己的编号追加各自的新行。
- 本次做了什么：一句话概括，人话可懂。
- 产出/改动文件：写相对项目根的路径，多个用顿号分隔。
- 关键决策与接口约定：**本列是其他 agent 最需要的一列**。写清新接口的签名/命名/规则，例如「flag 统一命名 `met_<char_id>`」「单抽成本常量 100，读取配置不硬编码」。
- 验证证据：MCP 日志、截图、手算对照等，一行可证。
- 遗留问题/待办：写清「谁在等什么」；没有就写「无」。
- 需通知的下游岗位：按 §3 映射表判断谁依赖你这次的产物。

### 4.5 交班流程（每个 agent 收工前）

```
完成本职输入/任务卡
  → 按 4.4 模板追加交接行（「Agent编号」列填自己的编号，规则见 §4.8）
  → 若改动了接口，确认「关键决策与接口约定」列写全
  → git commit（与任务卡同一 commit，信息如 "T0.3: CSV配表与加载管线"）并 push
  → 若下游任务卡正被其他 agent 等待，主动提示对方（交接表已更新）
```

### 4.6 接班流程（每个 agent 开工前）

```
读自己《岗位职责.md》
  → 读上游岗位的《交接班表》最后 5~10 行，确认：
     a) 依赖任务卡已验收通过（验收证据列有内容）；
     b) 接口约定与自己的职责文档一致（有冲突以「最新一行」为准并记录）；
  → 读自己主责的任务卡完整指令（推进表 §4）
  → 前置不满足时，先不开工，把缺什么写进自己交接班表并提示制作人
```

### 4.7 冲突处理规则

- 同一 CSV / 同一脚本被两个岗位修改：**以主责岗位为准**（见 §3 ◎），协作岗位只写自己职责列，不越权改他人字段；必须改时先在交接班表登记并通知主责岗位。
- 接口约定冲突：以**日期最新的交接行**为准，同时通知相关岗位和制作人。
- 数值与规则冲突：**系统策划的规则优先**，数值策划据此调数；**设定文档《初期设定》是最高裁决**，任何实现与设定冲突都必须停下并登记。

### 4.8 Agent编号规则（同岗位多 Agent 协作，所有岗位必须遵守）

同一岗位可以由**多个 AI Agent** 并行或接力交付工作（例如系统程序01 完成 T0.1~T1.1，系统程序02 完成 T1.2~T1.4）。为精确追溯与通知，约定如下：

1. **编号分配**：每个 Agent 上岗时分配岗位内唯一编号，格式 `<岗位名><两位序号>`，如 `系统程序01`、`系统程序02`、`系统策划01`。由制作人（或部署者）分配，首个上岗的 Agent 用 `01`。
2. **交接班表列**：所有交接班表统一 **9 列**，第 3 列为「Agent编号」，每行必填**实际执行该工作的 Agent 编号**（模板见 §4.4）。
3. **定位与通知**：接班、催办、冲突仲裁时定位到「岗位 + Agent编号」，例如「读系统程序交接班表 Agent编号=系统程序02 的 T1.4 行」；不再只说岗位名。
4. **接力交接**：同岗位换 Agent 接手时，接手 Agent 用**自己的编号**追加新行，不修改前任历史行；接班前先读本岗位交接班表最后几行确认前置（尤其前任 Agent 留下的接口约定与遗留问题）。
5. **登记新 Agent**：每有新 Agent 上岗，由制作人在《制作人_交接班表》登记一行（岗位 + Agent编号 + 分到的任务卡范围），确保全队可查。
6. **冲突处理**：沿用 §4.7——同岗位多 Agent 的工作以**日期最新的交接行**为准；接口约定冲突由制作人仲裁并登记。
